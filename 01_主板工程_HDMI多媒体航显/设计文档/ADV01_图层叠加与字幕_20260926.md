## 2. 这一版做了什么

进阶要求第 1 条是"图层叠加与字幕效果"。ADV01 只开这一项，其余进阶项
全部关闭，目的是让板级验证一次只对应一个要求：

| 画面位置 | 图层 | 内容 | 滚动速度 |
| --- | --- | --- | --- |
| 左上角 | 终端标识 | 航显终端标识 `ANLU TIS n/m`，n 为当前第几张，m 为卡内缓存的图片总数（最多 6） | 静态 |
| 右上角 | 时间戳 | 机场本地时钟 `TIME MM:SS`，每 60 个显示帧递增 1 秒，到 59:59 回零 | 静态（数值每秒变化） |
| 第 432..439 行 | 慢速细字层 | `EAST HALL OPEN  WEST HALL OPEN`，8 像素高青蓝色细字 | 每 2 帧左移 1 像素 |
| 第 448..479 行 | 主字幕带 | `FLIGHT ANU2026 GATE 12 BOARDING`，16 像素高白色粗字，带 alpha 渐变衬底 | 每帧左移 1 像素 |

实现方式是在 SDRAM 帧读出之后加一级叠加层 `rtl/ui_overlay.v`：底图先做
半透明压暗，再用片内 8x8 点阵字库把文字画上去。固定面板使用 50% 压暗，
底部字幕带使用从边缘 12/64 到中心 42/64 的逐行 alpha 渐变，背景仍是
实时图像，所以能明显看出"图上叠字"而不是全屏遮挡。主字幕为白色
`FFFFFF`，慢速细字层为青蓝色 `7FE7FF`，航显终端标识为青蓝色
`00E0FF`，时间是暖黄色 `FFD060`。慢速层使用固定 `alpha=20` 的深色
衬底，压暗强度比主字幕带更轻，两层叠在图上仍能看清各自的文字。
字符 ROM 完全在逻辑里，不需要外挂字库或 CPU。

慢速细字层复用了主字幕的 32 字符循环字模，但推进时钟只取
`scroll_pos[8:1]`，所以主字幕每帧左移 1 像素时它只移动半个像素的采样
位置，实际表现为每 2 帧左移 1 像素。两层方向相同、速度不同，就形成了
视差效果，同时文字内容仍保持机场航显场景。

混合不是只把颜色高低位截断，而是用 6 位 alpha 定点计算：

```verilog
out_channel = (base_channel * (64 - alpha) + 32) >> 6;
```

`alpha` 为 0 时保持底图，为 64 时完全压黑，`+32` 用于四舍五入。固定
面板取 `alpha=32`，也就是准确的 50% 压暗；底部字幕带的 32 行依次使用
16 个 alpha 等级，边缘透明一些、中心更暗，行 15 与行 16 使用同一中心值，
避免滚动时出现偶数行跳变。

## 5.1 出图前修掉的三处渲染缺陷

位流第一次构建完成后，又对着代码核算了一遍像素地址并做了预览图，发现
三处会让画面看起来"不对劲"的问题，都改掉并重新构建：

1. **字幕纵向重影**：字幕带高 32 像素，但行地址只取了 3 位
   （`(py - SUB_Y0) >> 1` 的低 3 位），字模会被上下重复画两遍。改成把
   16 像素高的文字居中放在 `SUB_Y0 + 8` 开始的 16 行里，只画一遍。
2. **徽标文字过大且互相重叠**：`text_char_hit` 的 `scale` 参数是
   log2 倍数，传 2 表示每个字符占 32x32 像素，而徽标里字符间距只有
   16 像素，相邻字母会叠在一起。改成与字幕一致的 2 倍（传 1），并把
   文字在 32 像素高的面板里垂直居中。
3. **衬底几乎没变暗**：`dim_rgb` 写的是 `{c[23:18], 2'b00, ...}`，只把
   每个通道的最低 2 位清零，白色 `FF` 只降到 `FC`，字幕压在图上看不出
   底色。改成用 6 位 alpha 做实乘加，固定面板取 `alpha=32` 得到真正的
   50% 压暗，徽标和字幕带才会呈现半透明深色衬底。

第 3 条是靠预览图发现的：先用仿真把叠加层单独渲染出来，再和真实机场图
合成，一眼就能看出"字压在图上但底没暗"。

## 5.2 每次换图后 3 秒重新计时

要求：不管是按 KEY1 手动换图，还是自动轮播换图，3 秒计时都要从 0 重新
开始数，而不是继续沿用上一张的节奏。原来的现象是"手动和自动各干各的"：
在 3 秒快到时按一下 KEY1，画面刚换完，自动换图又立刻跟上来。

原因在 `rtl/player_ctrl.v` 的缓存模式下：`timer` 被同一个 always 块里的
两处非阻塞赋值：

```verilog
// 修改前
if ((state == C_HOLD) && swap_wanted && !swap_pending &&
    (cache_count >= 8'd2)) begin
    swap_req     <= 1'b1;
    timer        <= 32'd0;        // 想在这里把计时清零
end
...
CC_HOLD: if (!swap_pending) begin
    timer <= timer + 32'd1;       // 但这一拍 swap_pending 还是 0
                                  // 自增在后面执行，把清零覆盖掉
end
```

换图的那一拍 `swap_pending` 还是 0，所以 `CC_HOLD` 也执行了自增；两处赋值
指向同一个寄存器，**后执行的那条生效**，清零被自增覆盖，计时器于是沿着
旧相位继续走。

修法是新增组合信号 `cache_swap_issue`，标识"这一拍正在把换图请求交给
SDRAM 帧缓存"，`CC_HOLD` 在这个信号有效时不参与计数，清零才生效：

```verilog
wire cache_swap_issue = (state == C_HOLD) && swap_wanted &&
                        !swap_pending && (cache_count >= 8'd2);
```

新增仿真 `sim/tb_player_key_restart_timer.v` 专门盯这件事：把
`HOLD_CYCLES` 缩到 200，在计到 150 时按一下 KEY1，然后测量"下一次自动
换图还差多少拍"。

| 版本 | 按键到下一次自动换图 | 判定 |
| --- | --- | --- |
| 修改前 | 46 拍（应为 200） | FAIL |
| 修改后 | 198 拍 | PASS |

顺手回归了其它和时序控制相关的仿真，全部通过：
`tb_player_cache`、`tb_player_key_immediate`、`tb_player_key`、
`tb_player_preload`、`tb_player_pipeline`、`tb_frame_store_cache`。

## 5.4 上板实测

2026-09-26 用 `hdmi_adv01_subtitle.bit` 在 HX4S20C 上实机运行，录了 8.65 秒
视频（960x540、29 fps），逐帧核对结果：

| 检查项 | 实测结果 | 判定 |
| --- | --- | --- |
| 六图轮播 | 左上角 `3/6 → 4/6 → 5/6 → 6/6`，每张约 2.7~3 秒 | PASS |
| 时间戳走时 | `TIME 04:29 → 04:37`，8.2 秒视频对应 8 秒计数 | PASS |
| 主字幕速度 | 相邻帧位移中位数 +2 像素（约 58 px/s） | PASS（设计 60 px/s） |
| 细字层速度 | 相邻帧位移中位数 +1 像素（约 29 px/s） | PASS（设计 30 px/s） |
| 双层速度比 | 2 : 1 | PASS（设计 2:1） |
| 半透明衬底 | 两层文字都清晰可见，底图没有被遮死 | PASS |
| LED 灯码 | `0010`（LED2 常亮） | PASS（真实图片显示基线） |

速度测法：从视频里按 29 fps 抽 87 帧，把白色层和青色层分别提取成横向亮度
剖面，对相邻帧做归一化互相关，取位移中位数。白色层 +2 px/帧、青色层
+1 px/帧，平均相关系数分别为 0.75 和 0.82。微信转码后的视频有少量丢帧，
按总位移求平均会偏低，所以这里用相邻帧位移的中位数。

实测确认本版不是"两层文字粘在一起"，而是真正按 2:1 的速度差在滚动。

## 6. 过程中修掉的一个坑

第一次构建时工程仍然指向基础版的 `constr/hdmi_mm_player.sdc`。ADV01 多
了一层封装，顶层里的时钟网络名字变成 `u_player/pixel_clk` 等，基础 SDC
里写的 `[get_nets {pixel_clk}]` 匹配不到任何对象，TD 报
`USR-8108 / USR-8159 create_generated_clock ... fails`，于是 4 个 PLL
输出时钟全都没建出来，布线后出现 64 个保持违例端点、Hold WNS -1528 ps
的假象。

修法是新增 `constr/hdmi_adv01_subtitle.sdc`，时钟定义与基础版完全相同，
只把网络引用限定到 `u_player/` 一层，并用
`scripts/check_adv01_constraints.tcl` 确认不再出现 CRITICAL-WARNING。
换回真实约束后保持余量回到正值，说明当时是约束写错而不是逻辑有问题。

`scripts/check_adv01_constraints.tcl` 里不再调用 `update_timing` 和
`report_timing_status`：这个 TD 版本在没有布局的设计上跑这两条命令会
直接 coredump 生成 `minidump-*.dmp`，只看 SDC 是否解析成功就够了。
