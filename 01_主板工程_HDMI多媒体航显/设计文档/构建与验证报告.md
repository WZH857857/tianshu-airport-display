>
> 本轮定位并修复了 `rtl/sdram/frame_store.v` 的两处问题：
>
> 1. **最后一像素前的空档被误判为文件提前结束**。BMP 解析器在发出最后
>    一个像素前还要先收完 3 个字节，`img_valid` 在这段时间会短暂为 0；
>    旧逻辑在 `wcnt == FRAME_LAST` 且 `img_valid=0` 时立刻重建整帧，导致
>    最后一个像素和 `last` 描述符永远写不进去。现在只在 `img_active`
>    真正撤销或解析器报错时才放弃当前帧。
> 2. **命令 FIFO 的寄存器读数据少等了一拍**。`async_fifo` 的 `rd_data`
>    是寄存器输出，旧状态机在 `rd_en` 生效的同拍就采样，拿到的仍是上一条
>    描述符；写引擎因此永远看不到最后一条 `last=1`。现在增加 `M_LATCH`
>    状态，正确锁存每一条描述符。
>

## 2. 本次解决的问题

### 2.1 TD 无法约束 PLL 输出时钟

**现象**

最初的 `.sdc` 用 `create_clock` 直接约束 PLL 引脚
（`get_pins {u_pixel_pll/pll_inst.clkc[0]}` 等），TD 报
`USR-8106 create_clock: cannot find target source pin`，
三个生成时钟一个都没建起来，整份时序报告把 125 MHz 的串行器、
25 MHz 的视频逻辑和 50 MHz 的系统逻辑全部塞进 `sys_clk` 一条 20 ns 约束里，
报告里的负余量因此完全不可信。

**诊断**

1. 官方《时序约束用户手册》SWUG200 给出的标准做法是
   `create_clock`（输入时钟）+ `derive_clocks` + `rename_clock`。
   照抄后 TD 打印出正确的频率推算：

   ```text
   Derived clock: create_generated_clock -name {pll_inst.clkc[0]} ... -multiply_by 2.5000 [get_pins {pll_inst.clkc[0]}]
   USR-6001 WARNING: No pins matched 'get_pins pll_inst.clkc[0]'
   USR-8108 CRITICAL-WARNING: create_generated_clock: cannot define a generated clock without targets.
   ```

   即 TD 已经算出了正确的分频 / 倍频系数，但它生成的引脚路径 `pll_inst.clkc[n]`
   丢掉了父层，匹配不到任何对象；手工写成完整层次路径
   `u_pixel_pll/pll_inst.clkc[0]` 同样匹配不到。
   `derive_clocks -instance [get_cells {u_pixel_pll/pll_inst}]` 也一样失败。

2. 时钟**网络**没有这个问题：

   ```text
   get_nets pixel_clk      -> pixel_clk pixel_clk
   get_nets pixel_clk_5x   -> pixel_clk_5x
   get_nets audio_mclk     -> audio_mclk
   ```

**修改**（`constr/hdmi_mm_player.sdc`）

用 `create_generated_clock` 把生成时钟定义在时钟网络上，
倍频 / 分频系数取 TD 自己推导出的数值：

```tcl
create_clock -name sys_clk -period 20 -waveform {0 10} [get_ports {sys_clk}]

create_generated_clock -name {pixel_clk_5x} -source [get_ports {sys_clk}] \
    -master_clock {sys_clk} -multiply_by 2.500 [get_nets {pixel_clk_5x}]
create_generated_clock -name {pixel_clk} -source [get_ports {sys_clk}] \
    -master_clock {sys_clk} -divide_by 2.000 [get_nets {pixel_clk}]
create_generated_clock -name {audio_mclk} -source [get_ports {sys_clk}] \
    -master_clock {sys_clk} -divide_by 4.067 [get_nets {audio_mclk}]
```

**验证**（`scripts/check_constraints.tcl`）

```text
CONSTRAINT CHECK: clocks = audio_mclk pixel_clk pixel_clk_5x sys_clk
clk0: 25.000 MHz 418 fanout pixel_clk
clk1: 50.000 MHz 265 fanout sys_clk
clk2: 125.000 MHz  28 fanout pixel_clk_5x
clk3:  12.294 MHz  13 fanout audio_mclk
```

### 2.2 异步时钟分组被拆开写导致误判

时钟建起来之后，布线报告里仍有一个
`Path Group: audio_mclk -> pixel_clk，Type: Same Domain` 的路径组，
3 个违例端点，最差 -0.884 ns：

```text
Begin Point : u_audio_tone/S_note_idx_reg[0].clk        (audio_mclk)
End Point   : u_i2s_receiver/S_i2s_bclk_1d_reg.mi[0]    (pixel_clk)
```

这条路径本来就是异步的：`I2S_receiver.v` 用 `S_i2s_bclk_1d/2d/3d`
三级同步器接收音频域的 BCLK / LRCK / DOUT。原因是原先把时钟分组写成三条
`set_clock_groups` 命令，TD 6.2.1 对同一批时钟的多条分组命令处理不完整，
只排除了其中一部分组合。

合并成一条命令后，该路径组从报告中消失：

```tcl
set_clock_groups -asynchronous \
    -group [get_clocks {sys_clk}] \
    -group [get_clocks {pixel_clk}] \
    -group [get_clocks {pixel_clk_5x}] \
    -group [get_clocks {audio_mclk}]
```

跨域结构（均在 RTL 中可查）：

| 跨域 | 同步方式 |
| --- | --- |
| `sys_clk` <-> `pixel_clk` | `frame_store` 格雷码异步 FIFO + toggle 同步器 |
| `audio_mclk` -> `pixel_clk` | `I2S_receiver.v` 三级同步器 |
| `pixel_clk` -> `pixel_clk_5x` | `lane_lvds_10_1.v` 二分频 toggle 同步后门控并串转换装载 |

### 2.3 `dir_lba` 组合路径超时

**现象**：约束修好后，布线报告 17 个违例端点，全部集中在 `u_fat32`：

```text
Slack        : -1.188ns
Begin Point  : u_fat32/sel18_syn_1126.clk
End Point    : u_fat32/dir_lba_reg[29]_syn_4.a[0]
Data Path Delay : 20.908ns   Budget 20.000ns
Logic Level  : 17 ( ADDER=6 LUT5=3 LUT4=3 LUT3=2 MULT18=1 LUT1=1 DRAM=1 )
```

一个周期里串了：扇区缓存 RAM 读出 -> 32 位减 2 -> 32x8 乘法 -> 32 位加法，
其中 `MULT18` 本身就要 3.56 ns。

**修改**（`rtl/storage/fat32_file_reader.v`）

跟随簇链时不再在一个周期里算出目录 LBA，而是拆成两级：

```verilog
S_DFAT_LATCH:  next_cluster <= fat_value;             // 只寄存 FAT 表项
               after_release_state <= S_DIR_LBA_MUL;

S_DIR_LBA_MUL: cluster_lba_off <= (next_cluster - 32'd2) *
                                  {24'd0, sectors_per_cluster};

S_DIR_LBA_ADD: dir_lba <= data_start + cluster_lba_off;
```

用寄存器里的 `next_cluster` 取代 RAM 输出，同时把乘法和加法分开，
路径被拆成「减 + 乘」和「加」两段。

**效果**：门级 SWNS 由 -3.251 ns（修改前那次构建）变为 +1.159 ns，
布线后 +1.160 ns。

### 2.4 引脚与官方手册逐项对照

官方例程 `vendor/lab_ex5_i2s/.../pin.adc` 用的是 **HDMI B 口**
（CLK C3、D0 G5、D1 F1、D2 E1、SCL P2、SDA R2），
本工程用的是 **HDMI A 口**，两套点位不同，容易误判成约束写错。
已按《HX4S20开发板手册-HDL版2410.pdf》第 2 章的引脚表逐项复核：

| 资源 | 本工程约束 | 手册引脚表 | 结论 |
| --- | --- | --- | --- |
| 系统时钟 | R7 | ⑲50M 时钟源：CLK = R7 | 一致 |
| HDMI A 口 | K1 / B3 / E3 / F5 / P1 / R1 | ④HDMI 接口A：CLK_P K1、D2_P B3、D1_P E3、D0_P F5、SCL P1、SDA R1 | 一致 |
| 4 个独立 LED | A4 / A3 / C10 / B12 | ②4 组 LED：LED1~LED4 = A4 / A3 / C10 / B12 | 一致 |
| 按键 | A2（切图）、B1（复位） | ⑯4 组按键：KEY1 A2、KEY3 B1，按下为低 | 一致 |
| TF 卡 | A12 / A14 / A13 / B14 | ⑰TF 卡槽：DAT3(CS) A12、CLK A14、CMD(MOSI) A13、DAT0(MISO) B14 | 一致 |

手册原文说明开发板两个 HDMI 口都可作输入或输出（A 口直连 FPGA，
B 口同样直连），因此选 A 口只影响插线位置，不影响功能。

### 2.5 纯白屏：视频复位被音频 PLL lock 拖住（板级问题）

**现象**

工程下载后显示器是**均匀纯白**，插拔 HDMI 线不变；同时板上绿灯为
`LED1` 闪、`LED2` 常亮、`LED3` 灭、`LED4` 常亮，红灯只是 5 V 电源指示。
把官方 HDMI 例程下载到同一块板、同一台显示器、同一根线、同一个 `HDMI_A` 口，
画面正常，说明板卡、线材、显示器、HDMI 口都没有问题。

**诊断**

1. 白色不是本工程的像素数据。`frame_store` 在 FIFO 欠载时输出
   `24'h10_20_30`，内置兜底图形是竖向彩条，两者都不可能是纯白。
   纯白是显示器收不到有效 TMDS 时的无信号底色。
2. 顶层原有这一行：

   ```verilog
   wire rst_hdmi = ~sys_rst_n | ~audio_pll_lock;
   ```

   音频 PLL 只要没锁，`rst_hdmi` 就恒为 1，`video_timing_640x480`、
   像素延迟寄存器和整条 HDMI 发送链路全部被按在复位里，
   不可能产生任何 TMDS 输出。这一条与"图片是不是白色的"完全无关。
3. 原 LED 映射把四类失败并到同一个灯上，现场无法区分原因：

   ```verilog
   assign led[0] = heartbeat[22];
   assign led[1] = frame_ready;
   assign led[2] = card_ok;
   assign led[3] = file_error | sd_init_error | cal_fail | pix_underflow;
   ```

**修改**（`rtl/hdmi_mm_player.v`）

视频复位与音频 PLL 解耦，并把诊断灯拆开：

```verilog
wire rst_hdmi = ~sys_rst_n;          // 音频 PLL 不再参与视频复位

assign led[0] = heartbeat[22];       // LED1 心跳
assign led[1] = audio_pll_lock;      // LED2 音频 PLL 锁定
assign led[2] = file_error | sd_init_error;   // LED3 卡 / 文件错误
assign led[3] = cal_fail | pix_underflow;     // LED4 SDRAM / 欠载错误
```

这样音频 PLL 出问题时只影响声音，画面通路照常工作，而且 `LED2` 会把
"音频 PLL 到底锁没锁"直接报出来，不会再把故障合并进画面问题里。

**新的上板判读顺序**

| 现象 | 结论 | 下一步 |
| --- | --- | --- |
| `LED1` 不闪 | bit 没进 FPGA，或 50 MHz 输入时钟没到 | 检查下载流程与时钟，不要动图片 |
| `LED1` 闪、`LED2` 灭 | 视频在跑，音频 PLL 没锁 | 只影响声音，画面按下面继续查 |
| `LED3` 亮 | 卡初始化 / FAT32 / 文件错误 | 查卡、分区、图片格式 |
| `LED4` 亮 | SDRAM 校准失败或像素欠载 | 查板级存储通路 |
| 灯正常但仍纯白 | 问题在 HDMI 时钟 / TMDS 侧，与图片数据无关 | 绕过卡和 SDRAM，把固定图形直接送进发送核分层定位 |

**下载注意**

必须用 `PROGRAM_SRAM`。本板掉电后会从配置 flash 重新加载旧设计，
断电或按电源开关会让屏幕现象退回旧 bit 的样子，容易误判成新 bit 无效。

### 2.6 标准测试图

`sdcard/IMG01.BMP` ~ `IMG05.BMP` 是专门做的判读图，画面上应当能看到：

1. 最外圈 **1 像素白边框**；
2. 两条 **白色对角线**（左上到右下、右上到左下）；
3. 左上角 **N 个 18 x 18 的白色小方块**，N 就是图片编号，

## 5. 未完成事项与风险

1. **13:39 双缓冲索引修正版等待重新上板确认**。13:13 版已经证明五张 BMP
   能显示、`KEY1` 能切图、稳定状态码为 `0010`；13:39 版只修改了双缓冲
   索引选择，目标是在保持这些功能的同时消除切图时由下向上的覆盖过程。
   上板后仍需逐张核对测试图的边框、对角线、小方块等视觉细节。

   **音频一律不做板级测试**（按既定要求不接线、不听声），音频只保留仿真证据。

2. **时序余量偏薄**。本次 HWNS 只有 +0.011 ns，而 `sys_clk` 的可达频率
   50.924 MHz 只比约束的 50 MHz 高 1.8%，都在"贴着过"的范围。
   违例端点为 0、功能上够用，但长期运行建议换 seed 重跑布线，
   或对 `u_sector_reader` 的 RAM 地址路径做一次流水化，把余量拉大。

3. **异步跨域依赖同步器结构正确**，不是靠忽略路径。
   上面表里的三种同步器都在 RTL 里可以逐行核对；
   如果后续改动破坏了同步器结构，`set_clock_groups` 会掩盖真实问题。

4. **HDMI 发射核与 TMDS 编码是官方加密网表**，无法检查内部实现，
   只能保证接口时序约束和仿真行为。

5. **TF 卡内容已经电脑侧核对**。卡已格式化为 FAT32 / MBR，根目录存在
   `IMG01.BMP` 至 `IMG05.BMP`；源文件和卡上文件的 SHA256 一致，且均为
   640 x 480、24 bpp、未压缩、像素偏移 54。`sdcard/` 中保留同一组
   测试图，便于以后重建卡。

6. 工程根目录残留 3 个 `minidump-*.dmp`（诊断时钟约束时 TD 自身崩溃产生）
   和一个名为 `$null` 的空文件（命令行误重定向产生），都与设计无关，
   自动删除被本机策略拦截，提交前请手工删除。

7. **板子掉电会退回旧设计**。本板配置 flash 里存的不是当前工程，
   断电或按电源开关后重新上电，FPGA 会加载旧 bit，屏幕现象随之改变。
   每次测试都要重新 `PROGRAM_SRAM` 下载，不要靠断电复位。
