# KEY1 切图错乱修复（V4，2026-09-25）

## 现象

图片自动轮播正常，但短按 `KEY1` 后偶尔出现旧图和新图混合、上下拼接、
半张图或错误颜色。问题与 HDMI 接收端无关，发生在 BMP 装载和 SDRAM
双缓冲换帧的交界处。

## 根因

1. BMP 解析器在装载过程中忽略新的 `start` 脉冲。
   `KEY1` 中止当前图片并请求下一张时，解析器仍停留在上一张图片的
   行、列、字节计数和像素状态中，下一张图片会被从错误位置继续解析。

2. 帧缓存中止清理不及时。
   旧实现要等 `abort_cnt` 计数到 `24'hFF_FFFF` 才清理写侧状态。
   下一张图片可能在清理完成前就开始写入，导致写 FIFO 或写调度器
   携带旧数据。

3. 满帧末尾的提交竞态。
   如果 `KEY1` 恰好发生在最后一个像素已写入 FIFO、`wr_done` 已置 1，
   但 SDRAM 的 `write_finish` 还没有提交时，旧条件 `img_abort && !wr_done`
   不会中止，旧帧仍会在下一张图片开始后提交。

4. `frame_store.v` 中 `write_abort` 在声明前被端口引用，TD 报
   implicit-net 关键警告。这个警告会让写 FIFO 的中止信号在网表中
   不可靠。

## 修改

| 文件 | 修改 |
| --- | --- |
| `rtl/player_ctrl.v` | 新增 `frame_abort`，在 `C_LOAD_REQ`、`C_LOADING`、`C_RESTART` 收到 `KEY1` 时输出中止脉冲。 |
| `rtl/hdmi_mm_player.v` | 将 `player_ctrl.frame_abort` 连接到 `frame_store.img_abort`。 |
| `rtl/sdram/frame_store.v` | 新增 `img_abort`；立即清空写请求、pending load、写计数、写完成和写 FIFO 调度；显示缓冲区和上一张完整图片不受影响；修正 `write_abort` 声明顺序。 |
| `rtl/sdram/vendor/frame_read_write.v` | 新增 `write_abort`，只复位写调度器和写 FIFO，不复位读侧/显示侧。 |
| `rtl/storage/bmp_stream_parser.v` | 接收到新的 `start` 脉冲时，即使 busy 也从干净的头、行列和字节状态重新开始解析。 |
| `sim/tb_frame_store_swap.v` | 增加半帧中止和满帧末尾中止检查；在像素时钟域统计 `frame_loaded`。 |
| `sim/tb_hdmi_audio_chain.v` | 将固定仿真停止点的 LRCK 边沿检查改为 ±2 个边沿容差，消除末尾采样假失败。 |

## 下载与验收

1. 在 TD Programmer 中选择 `PROGRAM_SRAM`。
2. 下载时钟建议使用 `5 MHz`。
3. 不要选择 `PROGRAM_FLASH`；断电会从配置 Flash 恢复旧设计。
4. 稳定显示真实图片时，`LED4 LED3 LED2 LED1 = 0010`。
5. 短按 `KEY1`：`LED1` 约亮 0.5 秒，下一张图片完整显示。
6. 异常判据：不应出现半张旧图、半张新图、上下拼接、颜色块错位或
   一直停留在同一张图片。
7. 如果 V4 有异常，可回退到
   `hdmi_audio_release_AXIS_TIMING_V3_20260925.bit`，其 SHA256 为
   `72B00279D5359A38D62DD0E3A71682B702CF009582C15547B9F65EE7ED428ADF`。
