# 基于 EG4S20NG88 的摔倒检测：技术方案与实验结果

日期：2026-10-05
目标板：安路 EG4S20NG88（VF-E20NG88 开发板）
约束：全部算法在 FPGA 内部完成，无 MCU / 无软核 / PC 只用于离线调参

## 1. 为什么这块板子不能跑 YOLO

EG4S20NG88 的实际资源（数据手册 DS301 表 1-1-1）：

| 资源 | 数量 |
| --- | --- |
| LUT4 / FF | 19,600 |
| 18x18 乘法器 (DSP) | 29 |
| 嵌入式 RAM | 64 x 9Kb + 16 x 32Kb = 1,088 Kb (136 KB) |
| 分布式 RAM | 156,800 bit |
| 片内 SDRAM | 2M x 32 bit (8 MB) |
| PLL | 3 |
| 用户 IO | 71 |

以 YOLOv5n 为例：约 1.8 GOP/帧（416x416），30 fps 需要约 54 GOPS。
29 个 18x18 乘法器 @150 MHz 的理论上限约 29 x 2 x 0.15 = 8.7 GOPS，
即使 100% 利用也只有需求的 1/6；卷积层还受带宽与片上缓存限制，
实际利用率通常不到 20%。更关键的是安路 TD 工具链没有 CNN 编译器，
卷积阵列、量化、层调度全部要手写 RTL。

结论：EG4S20 上跑 YOLO 不可行，不是"优化一下就行"的量级差距。

## 2. 采用的算法

**基于运动检测与形态学分析的摔倒检测算法**（Motion + Morphology Fall Detection）。
不使用神经网络，全部是整数运算与比较器，可逐级对应到 RTL：

```
DVP 摄像头 -> RGB 转灰度
  -> 按轴整数倍盒式降采样，统一归一化到 320x240 工作分辨率
  -> 帧间差分 |cur - prev| > 10
  -> disk(2) 腐蚀(两次 3x3 十字级联，去噪 + 断开人群) -> disk(2) 膨胀(把四肢粘成一个整块)
  -> 行投影 -> 最长行游程 -> 只在该行带内做列投影 -> 包围盒(x,y,w,h,area)
  -> 姿态塌陷状态机 -> 报警
```

两个设计细节值得记录：

- **统一工作分辨率**：数据集里既有 640x480 也有 1280x720 的片段。
  按轴取整数倍盒式降采样（640x480 用 2x2，1280x720 用 4x3）归一化到
  320x240，否则面积、高度这些阈值在不同清晰度下完全不可比。
- **两遍投影**：先找行方向最长游程，再把列投影限制在这一行带内。
  如果两个轴各自独立取最长游程，吊扇、传感器噪声等无关运动会把包围盒
  撑到整帧（实测在 720p 片段上会让包围盒变成 165x216 的假大块）。

### 2.1 多目标扩展（人群场景）

机场场景人一多，单靠"最大运动块"会不断在几个行人之间跳来跳去。前端改成
**固定 4 槽的排除式投影**（`fpga/rtl/multi_bbox.v`，已通过 RTL 对拍）：

| 步骤 | 做法 | 代价 |
| --- | --- | --- |
| 1 | 行投影找最长游程，确定一个运动连通域所在的竖直带 | 复用单目标的直方图 |
| 2 | 该游程做列投影 -> 包围盒，输出到 1 号槽 | 一次列扫 |
| 3 | 把这个连通域的矩形从掩膜里抠除 | 一次行扫（原地清位） |
| 4 | 在剩余像素上重复 1-3，直到填满 4 槽 | 最多 8 个候选 |

**为什么不用连通域 top-4（改方案的原因见 2.3）**：连通域标记需要一张和
掩膜同尺寸的标签图，或者给每个游程建 label 等价表，两种开销在
EG4S20NG88 上都不成立。**每条轨迹带一套独立的 `PostureMachine` 上下文**
（RTL 里是 `posture_bank`：1 份 `posture_fsm` 分时服务 4 个槽，4 套上下文
各存各的参考框和恢复窗），所以一个人坐下不会重置旁边另一个人的站立参考，
而面积只有 4 份并行状态机的三分之一。

已知短板：排除顺序由上一轮游程长度决定，密集人群里槽号会串（crowd05 的
逐帧同槽匹配率只有 24.8%）。轨迹的 IoU 重编号是下一步，见第 5 节。

### 2.2 判别规则

对每条轨迹的运动块维护两个量：

- `h_ref`：最近见过的最高的直立姿态（身高参考），带 300 帧有效期；
- `last_tall`：最后一次"还算直立"（h >= 0.60 x h_ref）的帧号。

当以下条件同时成立、且连续满足 `confirm_frames` 帧时报警：

| 条件 | 含义 | 阈值 |
| --- | --- | --- |
| `ratio <= lying_ratio` | 当前块不再竖长（宽高比） | 0.95 |
| `h <= collapse_frac x h_ref` | 高度塌到原来的 2/3 以下 | 0.65 |
| `cy - ref_cy >= drop_frac x H` | 重心明显下移 | 0.04（约 10 px） |
| `frame - last_tall <= collapse_frames` | **塌陷足够快** | 18 帧 |
| `h_ref.area >= min_ref_area` | 参考姿态是人不是小车 | 1600 px |
| `h_ref.h >= min_ref_height` | 参考姿态有人的高度 | 25 px |
| `obs.bottom >= ref.bottom - 0.15 x ref.h` | 倒下后底边仍在"地面"附近（腿部分离的游走块会底边上跳，被这条挡住） | 0.15 |
| `obs.area >= 0.30 x ref.area` | 倒下掩膜不能只剩小碎片 | 0.30 |
| 连续帧数 | 抗单帧抖动 | 单人 2 帧 / 人群 4 帧 |

`collapse_frames` 这一项是区分"摔倒"和"慢慢坐下"的关键：摔倒时身高塌到
2/3 以下通常在 1 s 内完成，而坐下要更久。所有时间窗都按视频帧率换算
（`Params.for_fps`），1 fps 的 CCTV 抽帧和 60 fps 的密集人群用同一套参数
语义：单人场景塌陷窗 1.20 s、确认 2 帧；人群场景确认 4 帧。

报警后还有一次**恢复撤销**：如果人在 `recovery_window` 内又站起来
（头顶回升或高度/宽高比回到直立），取消报警而不是发出去。
空档（无运动）会清零平躺计数，避免碎片跨遮挡接上别人的塌陷过程。

### 2.3 被实验否掉的做法

- **"包围盒必须变宽"**：朝镜头方向倒下时，运动掩膜只覆盖身体的一部分，
  包围盒不会变宽。加上这个条件会让 15 段样本中的 3 段漏报，已关闭。
- **背景建模（滚动最小/中值/带门限更新）**：机场里人可能一开始就站在画面里，
  背景建模会把人吸收进背景导致完全漏报。改为纯帧间差分，只关心
  "正在运动的块"，天然避开这个问题。
- **连通域标记 top-4**：先跑了游程密度统计（`fpga/tools/run_stats.py`，
  结果在 `out/crowd_stats.txt`），crowd 素材在 320x180 下平均每帧
  658~1091 条游程、p95 超过 1400 条；ERAM32K 又已经被上一帧缓存占满，
  标签图放不下，因此改成上面这套排除式投影。

## 3. 实验结果

### 3.1 GMDCSA24 全量回归（最终参数）

评测脚本 `tools/batch_eval.py`，报告 `out_frames/batch_report_final3.json`：

| 指标 | 结果 |
| --- | --- |
| 摔倒片段检出 | **14 / 15** |
| 日常动作(ADL) 误报 | **0 / 10** |

ADL 集合里包含坐下起立、弯腰捡手机、床上翻身、走路等最容易误报的动作
（Subject 3 / ADL / 07 坐下起立已单独复测，无误报）。

唯一漏报：

- **Subject 4 / Fall / 02**：视频开头人已经躺在床上，只有"从站立到倒下"
  才有可用的站立参考，这段不属于本算法覆盖的场景。

相比之下，早期版本漏报的 Subject 1 / Fall / 14（慢速侧倒）和
Subject 2 / Fall / 14 在把塌陷窗按帧率折算成 1.20 s 后都已修回。

### 3.2 人群视频回归

评测脚本 `tools/crowd_eval.py`，报告 `out_frames/crowd_report.json`。
人群素材为街景密集人流（均为"无人摔倒"负样本）：

| 片段 | 结果 | 最大同时跟踪 |
| --- | --- | --- |
| crowd01（1080x1920，完整） | 误报 0 | 4 |
| crowd02（60 fps，文件截断 2.22/4.87 MB） | 误报 1（1.98 s） | 4 |
| crowd03、crowd04（完整） | 误报 0 | 4 |
| crowd05、crowd06（文件不完整，各只解出 1-2 s） | 误报 0 | 1 |

对照：升级前的单目标版本在 crowd01 上有 **8 次误报**；加入多目标前端、
底边贴地门限、面积下限和人群 4 帧确认后降到 **0**。

crowd02 的这次误报发生在 60 fps、行人密度更大的画面里：相邻两个人的
运动团块粘连成一个 205 px 高的"假站立参考"，团块散开后被当成塌陷。
这是当前算法已知的机制性弱点（团块粘连），后续可以用"参考高度需连续
保持一段时间"的门限抑制，本轮为了保证已验证结果不动没有在线修改。

### 3.3 机场实拍 CCTV 事件

两段 1 fps 抽帧的 CCTV 确认事件（共 51 帧/51 s）：

| 事件 | 结果 | 说明 |
| --- | --- | --- |
| day6_event019 | 命中，第 26 s | 塌陷过程跨越 2 个采样帧，几何量足够 |
| day11_event001 | **漏报** | 人朝桌子方向倒下，被办公桌/转椅遮挡大半 |

day11 的漏报原因已定位：该事件整个倒下过程只被 1 fps 采到 3 帧
（第 6-9 s），运动掩膜被家具切得只剩一条窄碎片（41x108），宽高比
始终在 1.4-2.6，从未出现"扁平躺倒"形状；人停在地上不动后，
帧间差分不再有信号。**这是 1 fps 采样 + 家具遮挡的证据缺失，
不是实时 30 fps 部署下的典型形态**（30 fps 时同样的倒地约有
30 个样本，可完整观察形状变化）。机场实际部署接的是实时摄像头，
但这也说明：遮挡严重的机位仍需补"原地停住 + 重心贴地"的慢速判据。

另外 `crowd02/05/06` 仍在下载中（当前只有部分数据），
`crowd06` 下载在 1.29/5.72 MB 处被服务器断开，需要后续续传复测。

### 3.4 RTL 移植进展（整链 + 人群 4 槽已完成对拍）

`fpga/rtl/posture_fsm.v`：`PostureMachine` 的整数 Verilog 版，浮点阈值
全部改成整数交叉相乘（例如 `h/w <= 0.95` 写成 `20h <= 19w`），每条轨迹
一份实例。配套 `fpga/tools/rtl_check.py` 把 Python 前端喂给每条轨迹的
逐帧几何量录成向量，用 Icarus Verilog 仿真 RTL，比对**报警帧号**与
**每帧状态轨迹**：

| 片段 | 回放轨迹 | 结果 |
| --- | --- | --- |
| Subject1/Fall/13（含报警） | 4 | 一致 |
| Subject3/ADL/07（坐下起立） | 4 | 一致 |
| Subject4/Fall/02（已知漏报） | 4 | 一致 |
| day6 CCTV（1 fps，报警帧 26） | 2 | 一致 |
| crowd01（多目标，最长 200 帧轨迹） | 4 | 一致 |

合计 **18/18 条轨迹，报警帧与逐帧状态完全一致**。这验证了状态机的
整数化没有改变任何一个样本的行为。

像素前端也已经全部 RTL 化并逐级对拍到字节/逐位一致（灰度/降采样、
上一帧缓存、帧差、形态学、投影包围盒、整链报警），人群 4 槽版
（`multi_bbox` + `posture_bank` + `slot_scan`）同样完成对拍：

| 层次 | 素材 | 结果 |
| --- | --- | --- |
| 4 槽包围盒 `multi_bbox_check` | 合成 4 帧 + crowd01/crowd05 | 合成 4/4 IoU>=0.5（mean 0.827），crowd 素材与参考完全一致 |
| 人群整核 `multi_top_check` | crowd01 / crowd05 / Subject1-Fall-13，各 4 帧 | 4 槽框 + morph + diff + 4 路姿态逐帧一致 |
| 串口分槽 `tb_slot_uart` | 两组载荷快照 | 8 行 ASCII 全对 |

槽位顺序稳定性单独统计（`fpga/tools/multi_order_stats.py`）：crowd01
同槽匹配 51.6%、crowd03 64.2%、crowd05 只有 24.8% —— 槽号还没做重编号，
这是第 5 节第一条要补的。

残余风险：

- 极密人群中的团块粘连（见 3.2）；
- "站立状态下突然深蹲捡东西"尚无样本，真实部署前需补测；
- crowd02/05/06 与 day11 需要补全文件后复测。

> 以上是 PC 上的算法验证加 RTL 仿真对拍。整链（含人群 4 槽）已经在
> Icarus 仿真里逐帧比对通过，TD 综合/布局布线也跑出了面积与时序数字
> （见 `fpga/README.md`）；还差的是上板实测：真实 OV5640 画面 + 现场
> 标定。

## 4. 往 FPGA 上搬的预算

| 模块 | 存储需求 | 说明 |
| --- | --- | --- |
| 前一帧缓存 320x240x8bit | 614 Kb | 占 ERAM 的 57%，也可放片内 SDRAM |
| 运动掩膜缓存 320x240x1bit | 77 Kb | 两遍投影需要，占 ERAM 的 7% |
| disk(2) 膨胀行缓存 | 5 x 320 bit = 1.6 Kb | 分布式 RAM |
| 两级腐蚀列栈 | 2 x (3 x 320) bit = 1.9 Kb | 分布式 RAM |
| 列投影计数器 | 320 x 8 bit = 2.5 Kb | 分布式 RAM |

实际落地时降到 320x180（每 4 行丢 1 行），总存储 76,800 个 8 bit 条目
刚好够一帧差分加乒乓掩膜。TD 6.2.1 综合（`fall_camera_multi_top`，
EG4S20NG88）实测：

| 项 | 占用 | 比例 |
| --- | --- | --- |
| LUT | 10,104 / 19,600 | 51.6% |
| REG | 5,780 / 19,600 | 29.5% |
| ERAM9K | 48 / 64 | 75.0% |
| ERAM32K | 16 / 16 | 100% |
| DSP | 3 / 29 | 10.3% |
| 时序（48 MHz 约束） | SWNS +1.388 ns，HWNS +0.509 ns | 0 违例 |

面积大头仍是 4 槽包围盒（`multi_bbox` 4,533 LUT / 16 ERAM）。姿态部分
从 4 份并行 `posture_fsm` 改成 `posture_bank` 分时复用：整个 bank 1,367
LUT / 1,341 seq，其中状态机本体 1,137 LUT，比原来 4 份省下约 3/4。
像素时钟按官方 HDK 的 `cmos_pclk` 约束走 48 MHz（不是 HDMI 的
74.25 MHz），综合后 Fmax 51.427 MHz，最差路径已经不在 `multi_bbox` 里，
而是 `posture_bank` 内部的 `p_frame -> state`。

走完整 `board_multi_pnr.tcl`（默认种子，不需要 congestion 配方）后：
LUT 10,721/19,600（54.7%）、REG 6,036（30.8%）、slices 6,062（61.9%）、
SWNS **+2.000 ns**、HWNS +0.037 ns、**0 违例**、Fmax **53.098 MHz**；
同一次运行直接产出 `fpga/td/out_board_multi/multi.bit`。

### 4.1 RTL 模块划分（已落地）

1. `ov5640_capture` —— DVP 采集 + SCCB 配置（复用官方例程
   `06_Anlogic_Examples/03-4_CMOS_OV5640_Color_1280720`）→
   `rtl/cmos_capture_rgb565.v` + `rtl/ov5640_sccb_cfg.v`
2. `gray_front` —— 灰度 + 2x2 盒式降采样 + 3-of-4 行抽样（320x180）
3. `frame_diff` —— 上一帧缓存（ERAM32K 占满 + ERAM9K 一半）
4. `motion_morph` —— disk(2) 腐蚀（3x3 十字 x 2）+ 半径 2 圆盘膨胀，纯流式
5. `proj_bbox` / `multi_bbox` —— 单目标两遍投影 / 人群 4 槽排除式投影
6. `posture_fsm` / `posture_bank` —— 第 2.2 节的判别规则；单目标直接接，
   人群由 `posture_bank` 用 1 份状态机轮转 4 套上下文
7. `slot_scan` + `status_uart` —— 帧末把 4 槽快照分 4 行打给主卡
8. `led595_shift` —— 板载 LED（bit3 任一槽检出、bit4 任一槽报警）

还没做的：`track_assoc`（IoU 重编号，见 5）、`hdmi_overlay`（画框，
ERAM32K 已满，要先压缩灰度位宽或降显示分辨率）。

## 5. 下一步

1. **槽位重编号 tracker（FPGA 内）**：人群 4 槽已经能跑，但槽号会串
   （crowd05 同槽匹配 24.8%）。在 `multi_bbox` 和 `posture_fsm` 之间插
   一级 IoU 贪心关联，用上一帧的 4 个框给本帧 4 个框重排序，预算约
   500 LUT、不追加 ERAM；目标是 crowd05 同槽率 80%+；
2. **上板**：接 OV5640 跑实时画面，串口接主卡。`fall_camera_multi_top`
   的完整 P&R 已经跑完（默认种子布通，SWNS +2.000 ns / HWNS +0.037 ns /
   Fmax 53.098 MHz / 0 违例，slices 61.9%），可以直接出 bitstream；
3. **HDMI 画框**：ERAM32K 已满，画框需要先把灰度压到更低位宽或降显示
   分辨率，再复用官方例程 `01-1_EG4_HDMI_TX_Test_640480`；
4. **现场标定**：`MIN_REF_AREA` / `SUNK_CY2` / `COLLAPSE_FRAMES` 现在按
   30 fps 整定，机场远机位和近机位的人像像素尺度差很大，要用现场录像重
   标定一版参数并重跑整链对拍；
5. 补全 crowd02/05/06、day11 素材后复测，并针对团块粘连补门限。
